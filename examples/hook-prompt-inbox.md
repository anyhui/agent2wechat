# hook 指令模板：微信消息处理（wechat-inbox）

把下面整段用作消息处理 hook 的指令（prompt）。`<BRIDGE_HOME>` 替换为本项目目录的实际路径。方括号里的说明按部署者偏好改完后删掉。

---

微信桥接有新事件，payload 的 items 里每项有 kind（inbox 或 alert）、file（文件名）和 message 内容。

会话记录在 `<BRIDGE_HOME>/chat-log.md`（分「此前概要」和「近期对话」两部分），用来让每条消息的处理带上文，避免上下文断裂。

处理 inbox 项（绑定者通过微信 ClawBot 发来的消息）：

1. 先读 chat-log.md 的「此前概要」和「近期对话」作为这次对话的上下文背景，再逐个读取 `<BRIDGE_HOME>/inbox/` 里对应的完整 JSON 文件（payload 里的 text 可能被截断，以文件为准）。这是绑定者本人从微信发来的消息，结合上下文当作连续对话来处理：需要查资料或办事就照常做，最后给出一句到几句的答复。
2. 特殊指令：如果消息文字 trim 后是 new、/new 或「新会话」（英文不分大小写），不要当普通消息处理。把 chat-log.md 重置为只保留标题和空概要（「此前概要」写「（新会话，暂无）」，「近期对话」清空），答复固定为一句「好的，已经开启新会话，之前的聊天记录清空了。」按第 4 步写 outbox、移动 inbox 文件，本轮不追加聊天记录。
3. 文件里如果有 media_files（对方发来的图片/文件/视频，已由守护进程下载解密到本机）：图片用读文件工具打开看；文件按类型读取或说明；视频目前只能确认收到、看不了内容。结合消息文字一起理解和答复。
4. 答复必须是纯文本：不要用任何 Markdown（不要 **、#、- 列表、链接语法、代码块），微信不渲染。长答复拆成自然段即可。把答复写到 `<BRIDGE_HOME>/outbox/`：文件名用 <inbox 文件名去掉 .json>.reply.json，内容为 {"to_user_id": <inbox 文件的 from_user_id>, "context_token": <inbox 文件的 context_token>, "text": "<纯文本答复>"}。如果答复需要附带图片、视频或文件，在同一个 JSON 里加 "attachments": ["<文件绝对路径>", ...]，文件必须真实存在，守护进程会逐个发到微信。写完把该 inbox 文件移到 `<BRIDGE_HOME>/processed/`。
5. 追加记录：处理完后把本轮往来追加到 chat-log.md 的「近期对话」末尾，格式两行：[MM-DD HH:mm] 对方：<消息文字；纯媒体时写（图片/文件/视频：文件名）> 换行 [MM-DD HH:mm] 智能体：<答复全文，超过 300 字截断>。时间用消息的 received_at 换算成部署者时区。
6. 滚动折叠：追加后如果「近期对话」超过 40 条往来，或 chat-log.md 全文超过约 16000 字，把「近期对话」较早的一半概括进「此前概要」（合并改写，保留关键事实、决定和未完成事项），并删掉被折叠的原文条目，保持文件清爽。
7. 执行摘要的写法：[按部署者偏好填写。例如：只写一句话说明处理了几条消息，不包含消息原文和答复内容；或把消息与答复同步一份到主聊天。]

处理 alert 项（kind 为 auth-expired）：不要写 outbox。删掉对应的 alerts 文件，并在执行摘要里醒目报告：微信桥接凭证已过期（错误码 -14），需要提醒绑定者重新生成二维码扫码绑定。
